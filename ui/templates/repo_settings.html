Repository workflow

Set your policy in three steps

  1. Choose a profile. Start with the recommended preset, then run a baseline scan.
  2. Choose alerts. Notify a maintainer when an important issue is detected.
  3. Extend only where needed. Use version-controlled custom rules or advanced overrides.

Changing a policy affects future scans. Verified closure requires a subsequent scan of the updated revision.

Custom rules for this repository

Store .repository-detective.rules.json in the repository root and commit it with your code. The next scan checks the rule file and runs your matchers without downloading plugins or executing project scripts.

Use rules for project-specific architecture constraints, questionable loops, disallowed code patterns, tech debt, and security policies. Invalid rules stop the custom-rule scan rather than being silently ignored.

Rule configuration is reviewed through Git. See docs/CUSTOM_RULES.md for the complete format, limits, and example. A pattern match is a candidate finding, not proof of exploitation.

Build a custom rule — no coding required

Design a rule locally and download the JSON configuration. Review it and commit it to your repository; this tool does not modify your repository or run scripts.

Each pattern checks one source line. src/*.go matches files directly in that directory, not recursive subfolders; use a blank path to check all files. Expressions follow Go RE2 syntax.

Add a rule to generate a configuration file.

    Downloading or copying the file does not enable the rules. The server validates the committed file during the next scan. Keep a backup of existing rules when editing an established repository.
