# Repository reporting and repo-structure awareness

Repository Detective profiles each repository **before** scanners run and **normalizes every finding** before Gitea issue creation. Raw scanner output is never filed directly as issues.

## Repo profile detection

Each scan builds a `repo_profile` persisted on the scan summary. The profile includes:

| Field | Examples |
|-------|----------|
| Layout | `single_app`, `monorepo`, `nested_services`, `library`, `infrastructure`, `documentation`, `mixed` |
| Ecosystems | Go, Python, JavaScript/TypeScript, Docker, Kubernetes, Terraform, Ansible |
| Manifests | `go.mod`, `package.json`, `Dockerfile`, `.github/workflows`, `Chart.yaml` |
| Ignore paths | `vendor/`, `node_modules/`, `dist/`, `.terraform/`, `.venv/` |
| Reporting hints | `.gitea/ISSUE_TEMPLATE`, `CONTRIBUTING.md`, `SECURITY.md`, `CODEOWNERS` |

Monorepos are profiled by subpath using nested manifests (e.g. `apps/web/package.json`, `services/api/go.mod`).

## Reporting modes

Configure `reporting.mode` in `config/config.yaml`:

| Mode | Behavior |
|------|----------|
| `monitor_only` | Dashboard/report only — no Gitea issues |
| `high_signal` (default) | Auto-issue critical/high with medium+ confidence; suppress vendor/generated by default |
| `standard` | Critical/high issues; medium manual review unless high confidence |
| `strict` | Also auto-issue medium findings |
| `compliance` | Report most findings; still deduplicate and respect `max_issues_per_scan` |

## Finding actions

Every normalized finding receives a `reporting_action`:

| Action | Meaning |
|--------|---------|
| `auto_issue` | Create or update a Gitea issue |
| `manual_review` | Visible on dashboard; operator decides before filing |
| `report_only` | Dashboard/export only |
| `suppressed_with_reason` | Hidden from default views but auditable (`preserve_all_findings: true`) |
| `disabled_by_policy` | Scanner/category disabled by repo policy |

Findings are **never deleted silently**. Suppressed findings remain in scan data when `preserve_all_findings: true`.

## False-positive reduction

`false_positive_reduction` adjusts confidence and default actions based on:

- Source type (`source`, `test`, `docs`, `generated`, `vendor`, `example`, `config`, `dependency`)
- Line number reliability and file existence in checkout
- Dev-only dependencies
- Multi-scanner agreement (raises confidence)

### Default suppressions

Generated, vendor, minified, test fixture, and docs/example paths are downgraded or suppressed unless repo policy overrides:

```yaml
reporting:
  create_issues_for_tests: false
  create_issues_for_generated: false
  create_issues_for_vendor: false
```

## Issue creation gates

Gitea issues are created only when:

1. Finding passed normalization (not raw scanner output)
2. `reporting_action` is `auto_issue`
3. Severity/confidence meet `default_issue_min_severity` and `default_issue_min_confidence`
4. `max_issues_per_scan` not exceeded
5. No open issue with the same fingerprint exists

Issue bodies include severity, confidence, repo profile, false-positive risk, evidence, remediation, and fingerprint.

## Scanner applicability

Skipped scanners are recorded with an applicability reason (visible in scan health):

- `skipped_no_matching_files` — e.g. Go linter with no `go.mod`
- `skipped_tool_unavailable` — binary missing in container
- `skipped_disabled_by_repo_policy`
- `skipped_docs_only_repo`
- `skipped_generated_or_vendor_only`

Skipped scanners do **not** inflate repo finding counts.

## Overriding repo policy

Per-repo settings in the UI/API still apply (`policy_level`, `issue_policy`, severity/confidence gates). To force low or test findings into Gitea:

```yaml
reporting:
  mode: compliance
  create_issues_for_low: true
  create_issues_for_tests: true
  source_type_overrides:
    test: manual_review
```

## Monorepos

Repository Detective detects nested manifests and profiles each subpath. Scoped scans (PR/push) still run profile detection on changed paths; full scans list all repository files for layout detection.
